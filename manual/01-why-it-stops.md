# 第 1 章 なぜ止まるか——承認待ちの構造

## 1-1. 止まった実例から始める

2026 年 9 月 7 日、著者の環境で、あるエージェントのセッションがこう終わりました。

> サイジングの式を変更してよいか判断できないため、利用者の確認を待ちます。

セッションはそこで終わりました。判断を要していたのは「サイジングの式」という **1 点**です。
一方、そのとき進められたはずの作業はこれだけありました。

```
バックテストの実行・データの品質検査
監査（検証監査・判断監査）
実装・デバッグ・リファクタリング
別の戦略の設計
販売する道具の企画・生成・実装・測定
```

どれもサイジングの式とは関係がありません。**1 点の留保が、無関係な全作業を止めていました。**
しかもエージェントは正しいことをしたと思っています。「確認を取るべきことは確認を取る」は、対話で使っているときは美徳だからです。

無人で回すとき、この美徳がそのまま最大の故障になります。答える人がいないのだから、「確認を待つ」は「永久に止まる」と同じです。

## 1-2. 判断の留保と、作業の停止は別のもの

ここが本書全体の土台です。

```
判断の留保   ある 1 点について「自分では決めない」と決めること
作業の停止   セッション全体が進むのをやめること
```

対話で使っているとき、この 2 つは同じに見えます。人が横にいて、聞けばすぐ答えが返るからです。
「聞く」と「止まる」の間の時間がほぼゼロなので、区別する必要がありません。

無人にした瞬間、この 2 つの間の時間が数時間〜数日に伸びます。すると、

```
留保するべきもの   その 1 点に依存する作業だけ
続けるべきもの     それ以外の全部
```

という分割が要ります。分割しなければ、留保が停止に化けます。

「そんなことは分かっている」と思うかもしれません。しかし分割は、**都度の判断に任せると必ず安全側に倒れて全部止まります**。
エージェントは「念のため」を選ぶ立場にいるからです（1-5）。だから分割は、都度の判断ではなく、**あらかじめ書いた規則**として置く必要があります。

## 1-3. 承認待ちの 3 つの型

止まる場面を分けると、実際には 3 種類しかありません。

| 型 | 例 | 正しい扱い |
|---|---|---|
| A. 取り消せない外部関係 | 新しい販売プラットフォームへの登録、口座開設、決済手段の導入、規約違反の疑いがある行為 | **本当に人の判断が要る。**起票して、それに依存する作業だけ止める |
| B. 人の物理操作 | ボタンを押す、書類を出す、本人しか知らない値を答える、端末で 1 回クリックする | 人の判断は要らない。**人の手が空くまでの待ち**であり、起票して他を進める |
| C. 権限設定による遮断 | ツール側の許可リストに無いコマンド、編集を許可していないファイル | 判断の問題ではなく設定の問題。**遮断された内容を報告して、できる範囲を続ける** |

A 以外は「確認」の対象ですらありません。B は待ちで、C は設定です。
ところが、対話に慣れたエージェントは A・B・C を全部「確認を取るべき場面」として扱います。
そして A ですら、止めるべきなのは**その契約に依存する作業だけ**であって、セッションではありません。

著者の環境では、A に該当するのは 2 種類だけと決めてあります（第 7 章 CHARTER の骨子 §4）。

```
① 資金やリスクの前提そのものを変えるとき（式の構造・係数・許容度・資金ベース）
② 利用者の名義で新しい外部関係を結ぶとき（販路・口座・決済・規約違反の疑い）
```

**それ以外は全部、エージェントの裁量で進めてよい**と書いてあります。設計も実装も監査も公開も価格設定も。
「これをやっていいか」を聞く必要はなく、やってから記録すればよい、と。

これは大胆に見えますが、逆です。A の範囲を狭く固定しなければ、B と C が A に混ざり、全部が「念のため」になります。
**裁量の範囲を広く明文化することは、止まらないための前提条件です。**

## 1-4. 「依存範囲」を都度の判断に委ねない

A に該当したとき、何を止めて何を続けるかも、あらかじめ書いておきます。書かないと、安全側に倒して全部止める挙動に必ず戻ります。

著者の環境の実際の記述（第 7 章 CHARTER の骨子 §4「依存範囲の限定」）はこうです。

```
① 資金・リスクの前提が保留中のとき

  棚上げする（これだけ）
    実発注
    ロットサイズの変更
    保留中の前提に依存するサイジング計算

  続行する
    バックテスト・データ取得・品質検査
    監査（検証監査・判断監査とも）
    実装・デバッグ・リファクタリング
    戦略の着想・設計・事前登録の作成と改訂
    デモ稼働（実弾を伴わないもの）
    販売側の全作業

② 新規の外部関係が保留中のとき

  棚上げする（これだけ）
    その契約・登録の実行そのもの
    その契約が成立していることを前提とする公開・出品・入金導線

  続行する
    同じ商品・戦略の企画・生成・実装・測定
    既に持っている販路・口座を使う公開と出品
    他の販路・他の商品・他の戦略の作業
    調査・比較検討・提案の作成
```

そして最後に一行。**「列挙にないものは続行してよい。迷ったら続行し、記録する。」**

この一行が無いと、列挙は「これ以外は止める」と読まれます。既定を「進める」に倒すのは、ここです。

## 1-5. なぜエージェントは「念のため」を選ぶのか

エージェントが確認を選ぶのは、能力の問題ではなく**立場**の問題です。

- 進めて壊したときの責任は目に見える。止まって進まなかったときの損失は目に見えない
- 対話の訓練では「確認を取る」が褒められる。「聞かずに進んで正解だった」は褒められない
- 無人実行では、止まったことに気づく人が数時間いない。止まった側のコストが、エージェントには一切返ってこない

したがって「念のため確認します」で終わるのは、**エージェントにとって常に合理的**です。
説得で直りません。直すには、

```
1. 「念のため確認します」で終わるのは規律違反である、と明文化する
2. 聞きたいことを置く場所（PENDING）と、答えが返る経路（INBOX＋フック）を用意する
3. 終了しようとしたとき、未読があれば機械が差し止める
```

の 3 つが要ります。1 は文書、2 と 3 は機構です。文書だけでは守られません（第 6 章 6-9）。

## 1-6. 無人実行（`-p` モード）で特に起きること

Claude Code を `-p`（print モード）で起動すると、対話の質問系ツールは無効になります。
つまり**エージェントが人に質問する手段は、設計上もう存在しません**。それでもモデルは質問文を書き、そこで応答を終えます。
応答が終わればプロセスは終わり、次に人が起動するまで何も起きません。

著者の環境の規則は、無人実行についてこう書いています。

```
□ 棚上げ条件（1-3 の A）以外の確認質問をしない（「コミットしますか」等）。判断して進めること
□ A に該当する場合は PENDING に書いて棚上げし、依存しない作業を続ける。終了しない
□ ツール側の権限設定でブロックされた場合、それは A ではない。可能な範囲で作業を続け、ブロックされた内容を報告に含める
```

**「念のため確認します」で終了するのは違反である。無人実行では特に、A 該当を理由に終了してはならない。答えられる者がいないのだから、棚上げして進む以外に正しい挙動はない。**

## 1-7. 棚上げが作る新しい失敗

ここまでで「止まらない」形はできます。しかし棚上げは、新しい失敗モードを 1 つ作ります。

**承認待ちを忘れる。**

停止は嫌でも目に入ります。止まっていれば人は気づきます。棚上げは違います。放っておいても作業が進むので、
聞かれたことに答えないまま何日も経ちます。そして棚上げの山が積み上がったとき、どれに依存する作業が止まっていたのか分からなくなります。

したがって棚上げには、**両側に気づかせる機構**が必要です。

```
人の側        音を出さない手段を第一にする
              1. 番兵ファイル  ルートに「!pending_3.txt」。名前そのものが件数。0 件で消える。
                              ファイル一覧を開くだけで目に入り、夜間でも何も鳴らない
              2. 通知          新規の未処理が発生したときだけ。同じ集合に二度鳴らさない。夜は翌朝に持ち越す
              3. ログの末尾    自動再開スクリプトの終了サマリに未処理件数を書く

エージェント側  4. セッション開始時のフックが未処理の件数と項目名を文脈に注入する
              5. 区切りごとに INBOX を読む。処理した行の行頭に ✔ を付ける（消さない）
```

「気づく仕組みのない棚上げは、ただの取りこぼしである」——著者の環境の CHARTER はそう書き、
**この機構が動かなくなったら棚上げ運用をやめて、停止条件に戻す**とまで書いています。機構が規律の前提条件だからです。

第 2 章で、この機構をファイル 2 つとフック 5 つで作ります。

## 1-8. 機械に守らせる場所

| 規則 | 文書に書く | 機械に置く |
|---|---|---|
| 裁量の範囲と A の 2 種類 | CHARTER §3・§4 | （文書のみ。ここは判断そのもの） |
| 依存範囲の固定 | CHARTER §4「依存範囲の限定」 | PENDING の書式が「棚上げする作業」「続行する作業」の両方を必須にする（第 2 章） |
| 「念のため確認します」の禁止 | CHARTER §4「無人実行時」・§7 | Stop フックが未読を差し止める（第 2 章）。権限は allow を広く・deny を厳しく（第 6 章 6-1） |
| 承認待ちに気づく | CHARTER §5-9 | 番兵ファイル・SessionStart の注入・通知（第 2 章） |

## この章の要点

- 止まる原因は「確認を取る」という美徳そのもの。無人では美徳が故障になる
- 判断の留保と作業の停止を分ける。留保は 1 点、停止は依存する作業だけ
- 何が留保の対象かを 2 種類に狭く固定し、それ以外は裁量と明文化する
- 依存範囲を都度の判断に委ねず、書いておく。「列挙にないものは続行」を既定にする
- 棚上げは「忘れる」を生む。両側に気づかせる機構が無ければ、棚上げをしてはいけない
